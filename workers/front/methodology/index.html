How the numbers are made

One store, several rendering architectures, one ruler. This page states every rule the published numbers follow — and, just as load-bearing, what those numbers cannot claim. If a rule here and a number on the site ever disagree, that is a bug: send me the URL.

Lab and field never mix

Two kinds of numbers exist here. Lab numbers come from scripted, throttled, repeated runs — they are the only numbers ever compared across architectures, because they are reproducible. Field numbers are the live readout of your own visit — the reality check, shown per page, never used to rank architectures (nobody controls who visits what). A bench run's beacons are captured by the harness and never reach the field collector, so lab traffic can't pollute field data either.

One ruler

The same pinned web-vitals build measures every page, lab and field, so TTFB, FCP, LCP, CLS and INP mean exactly the same thing everywhere. Bytes are read from the browser's own network accounting — compressed bytes actually transferred, including response headers, never decoded sizes.

Three published profiles

Every lab run applies one of three pinned test profiles at the automation layer: fast WiFi + laptop (project-defined — no widely-published WiFi preset exists), average broadband + desktop and slow 4G + mid-range phone (both pinned to Lighthouse's published defaults, the second with a 4× CPU slowdown). The exact values live in the versioned profile spec, and every receipt records what was actually applied, so a value change can never silently reframe an old number.

One batch, %%LAB_RUNS%% runs per cell, two cache columns

All architectures are measured in one batch — runs interleaved round-robin, so a noisy moment lands on every variant, not on whichever URL happened to be measuring. The published value is the median of %%LAB_RUNS%% runs, never a best-of, and every cell carries that median's min–max band across those runs so you can see when a gap sits inside the noise. One honest detail: a metric a run could not produce is recorded as absent rather than as a zero, so a cell's median is over the runs that produced a value — the receipt lists all %%LAB_RUNS%% either way, so the count behind any cell is checkable. Cold and warm are separate columns measuring the edge data tier; the browser cache is held constant instead — every run is a fresh browser context, a first-time visitor. The reading table publishes the WARM column — steady state, per ADR-0001's "warm as headline, cold as a labeled callout" — no matter what cache knob the page you are reading it on carries; the linked receipt holds the cold column beside it. Numbers publish as dated snapshots pinned to a commit, never live-updated.

What the bytes mean

Transferred bytes are bucketed — HTML, JavaScript, CSS, fonts, images, data — with initial JavaScript as the headline: that is where the render-axis story lives. Three rules keep the buckets honest:

  • Inline bytes count. A script inlined into the document is attributed to the JavaScript bucket by its share of the uncompressed document (an inlined bundle is not "0 KB of JS"). The stated limit: the share is exact only if every part compresses at the document's average ratio — a reproducible attribution, not per-byte compressed truth.
  • Serialized state is data, not code. A script tag the browser will not execute (JSON state, import maps) counts as data. The stated caveat that follows: React's App Router ships its hydration state as executable script, so it counts as JavaScript; Qwik ships equivalent state as inert JSON, so it counts as data. The initial-JS row therefore includes serialized hydration state for executable-payload frameworks and excludes it for inert-payload ones — a real asymmetry of the paradigms' own delivery choices, stated here rather than silently reclassified. No initial-JS comparison between two hydrating frameworks is published as a verdict without this caveat riding it.
  • The instrument strips itself out. The switcher/HUD chrome this site injects — its markup, stylesheet, font, and the ruler itself — is excluded from every bucket by known path, and the excluded bytes are reported in each receipt, so the exclusion is checkable, not vacuous.

The noise rule

Every cell publishes its median with the min–max band across that batch's runs, and every receipt carries the raw runs behind both. Comparative language — "faster", "lighter", any verdict — is permitted only where the compared bands do not overlap. Where they overlap, the site says exactly this: indistinguishable at this sample size. The publication pipeline enforces the rule mechanically: a fit sentence whose receipts don't support it fails the build.

The instrument's own cost

Byte-stripping removes the injected instrument from the counted bytes; it cannot remove the instrument's parse, style and font work from the timing metrics. So that cost is measured — the same page, with and without the chrome, both served compressed exactly as the plane serves them. %%CC_STATEMENT%% Every architecture carries the identical instrument, so no column gets a different strip. The constant itself, though, is one measurement of one page under one profile: it is the order of magnitude of what the instrument costs, not a per-variant or per-profile equality — a page that parses more before first paint absorbs it differently, which is the same reason throttled cells here carry no verdicts.

Where these runs execute

%%LAB_BATCH_STATEMENT%% The target environment this project records — a pinned, documented cloud runner, two geographic locations, and a WebPageTest cross-check — activates in a later unit.

Two consequences, binding until then. First: throttled-profile timing cells publish numbers, never verdicts — the throttle is request-level emulation (see the limits below) and the cross-check that would confirm a throttled verdict directionally does not exist yet, so the published fit line rides bytes, which no throttle touches. Second: official batches never run inside a deploy gate. The post-deploy smoke asserts receipt shape and provenance; a performance magnitude asserted on a shared CI runner would go red for reasons that are not regressions and block the plane for none.

Limits of this data

  • Throttling is CDP request-level emulation above the transport stack: no TCP slow-start, no connection setup, no request parallelism. That limit is not paradigm-neutral — it interacts with round-trip count — which is exactly why throttled cells carry no verdicts yet.
  • TTFB's travel/server split is attributed beneath the emulation (Chromium rebases navigation timing under throttle): compare the split across variants; never read it against the profile's emulated round-trip time.
  • The origin computes over a frozen crate of %%SNAP_COUNT%% releases (frozen %%SNAP_DATE%%): absolute server think-time and CPU are floors, not production magnitudes. Comparisons transfer; extrapolations don't.
  • Every lab number is a Chromium number.
  • INP is always INP (scripted): real event-timing entries under a named, scripted interaction — on the editorial surface, the page's one designed interaction, Add to cart, clicked with no warm-up click before it.
  • Post-load idle work is deliberately settled onto the load side before both the byte snapshot and the click. That is what keeps the initial/interaction split from varying run to run, but it has a stated consequence in both directions: a framework whose preloader runs at idle (Qwik) has those bytes counted in its initial-JS row, and the fetch half of any deferred handler binding is finished before the click, so the INP row reflects what remains at click time — resolving and running the handler, not downloading it.
  • Cost cells: none are published. The cost model prices CPU-ms from the deployed plane's own telemetry, which is not armed yet; a local CPU profile of a remote origin is refused by the harness outright.
  • The live field readout displays no percentile below fifty samples per segment — a portfolio's traffic is honest about being small.
  • Privacy: the field beacon carries variant, surface, environment, cache state and serving location. No identifiers, no cookies, no PII.

Reproduce it

Every published number links a receipt: profile, date, commit, run location, the exact URLs driven, and every raw run. The harness is public. One command re-runs any receipt's batch — same paths, profile, run count and interaction — and mints a new dated receipt: 

git clone https://github.com/Robert-Lark/project-matrix
pnpm install
pnpm bench reproduce <receipt.json> --origin https://pm-front.robresearch87.workers.dev

One honest caveat about that command. Each batch tags its URLs with a run-isolation nonce, and a reproduce mints a fresh one — so it drives the same pages under fresh cache state, not the identical URL strings. That matters on a live plane, because a brand-new URL's first hit is a cache miss served uncompressed, which inflates the first of the seven runs. Pass --nonce with the receipt's own environment.runNonce to re-drive the exact published URLs and warm them first; the receipt states this precondition itself.

The pre-release Remix 3 frontier build is excluded from every number by mechanism: the runner refuses any /remix3/ URL before it launches a browser, so a receipt naming it cannot exist. The Apollo misapplication exhibit is fenced by declaration for now — labeled on its surface, never given a column or counted in any cell — and the runner-side refusal that makes Remix 3's fence a mechanism extends to it when the catalogue surface it lives on is built.
