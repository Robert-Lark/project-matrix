## 3. What the verification pass found (`verify-slice wf_73fac766-f84`)

All four lenses completed; **twenty-five findings, every one confirmed by me against source
before acting, and every actionable one adopted.**

Ranked by what they would have cost:

1. **BLOCKER — the ADR's one named obligation on this Worker was missing.** ADR-0005's
   Consequences, verbatim at `docs/adr/0005-plp-data-strategy-comparison.md:203-205`: *"The
   x-pm-cache-state **pass-through** onto server-rendered HTML is the HTMX variant Worker's
   obligation (proven in the prototype's loaders leg)."* I dropped the edge response's
   headers. The bench runner reads that header off the **document** response into every
   receipt (`tools/bench-runner/src/collect.ts:928` → `docCacheState`, schema'd at
   `receipt.ts:51-52`); on every other arm the tray fetch is client-side and visible in the
   network log, but on this one it happens inside the Worker, so the document header is the
   only place the served condition can surface. Every htmx PLP receipt would have recorded
   `docCacheState: null` and the cold/warm split would have rested on the runner having
   *asked*. Implemented, with legs over `bypass`/`miss`/`hit` and one proving it invents
   nothing when the edge sent none.
2. **BLOCKER — a history-cache miss would have wiped the page.** I branched page-vs-fragment
   on `HX-Request` alone. htmx's Back-button restore re-fetches the URL **with that header
   set** (`historyRestoreAsHxRequest` defaults true, `htmx.org@2.0.10/dist/htmx.js:281`) and
   swaps the answer into `document.body` by `innerHTML`, so on a cache miss Back would have
   received the bare `.pm-plp` block over the whole page — shell, chrome slot and every
   script gone. htmx's own config doc names the trap at `htmx.js:277`. Fixed server-side
   (`HX-Request` present **and** `HX-History-Restore-Request` absent), not via the client
   config it suggests, because a server's correctness must not depend on a client file having
   loaded.
3. **BLOCKER — no current-page marker from page 6 on.** I copied the reference's
   `1..min(totalPages,5)` window literally, which is right for a renderer that only draws
   page 1 and wrong for one that does not: from page 6 the nav carried **no
   `aria-current="page"` at all** and offered no route past 5. Six clicks from the front page
   on the fixture; the crate has 21 pages. The window now slides, clamped to contain the
   current page; at page 1 it is still `1..5` (and `1..1` at n=240), which is why byte
   identity survived.
4. **BLOCKER — an out-of-range page read backwards.** The edge floors `page` at 1 with no
   ceiling, so `?page=11` answers 200 with empty `items` and the range rendered **"Showing
   241–240 of 240 releases"** — which `src/plp.js` would then have announced to a screen
   reader verbatim. Empty pages now show "0", and "Next" is emitted only when a next page
   exists — *except at page 1*, where the reference's unconditional link is reproduced
   deliberately (see §6).
5. **A number I had already written down was wrong.** "5,915 B / 6,525 B" were
   `String.length`. Corrected everywhere to `Buffer.byteLength` (5,936 / 6,554). The claim
   held; the figure was not re-derivable with `wc -c`, which on a surface with published
   receipts is not good enough.
6. **The enhanced path was strictly worse than the JS-off one on failure.** htmx maps a
   4xx/5xx to `{ swap: false, error: true }` (`htmx.js:267`), so with the data plane down a
   boosted click changed *nothing*: old grid, no URL push, no message — while the same click
   with JS off gets the branded 503. ADR-0005 §1's "(works JS-off)" is a parity claim, and a
   progressive enhancement must never fail in that direction. `plp.js` now announces
   `htmx:responseError` and `htmx:sendError` into the live region.
7. **This variant's own record said the opposite of the new code.**
   `variants/htmx/DIFF-TO-STARTER.md` still asserted, in bold, that htmx registers nothing and
   compares under `NO_NOISE`, and cited a `RUNTIME_SCRIPTS` constant that no longer exists
   (`grep -c RUNTIME_SCRIPTS variants/htmx/src/render.mjs` → 0). In my boundary; rewritten.
8. **A PLP failure marked *Editorial* as the current page.** `renderUnavailablePage` hardcoded

9. **A comment that the code refutes — mine, copied from the contract.** See §6.2.
10. **A `KNOWN LIMIT` comment under-counted** what varies above page 1 (two → three).
    Corrected.
11. **The tray's SHAPE was proven by nothing — the identity guard could not see it by

### 6.1 `workers/front/src/index.js` — partials trip the chrome-slot alarm (NEW, and that file predicted it)

Not one of the brief's three; it only exists once htmx serves partials.

The front Worker injects chrome into `div#pm-chrome-slot` on any `text/html` response and

**(i) The unconditional `rel="next"` (`plp.mjs:134`).** At n=240, `totalPages` is 1 and the

**(ii) `pageHref` drops the measurement condition, and its own comment says otherwise
(`plp.mjs:60-68`).** The comment claims these hrefs *"preserve the WHOLE condition
(URL-as-receipt, ADR-0004 §5)"*. They build a fresh `URLSearchParams` carrying `page` and — only
when it differs from the default — `n`. A query-only relative reference **replaces the entire
query** (RFC 3986 §5.3; verified: `new URL("?page=2", ".../plp/?cache=cold&run=bench-7&n=240")`
→ `.../plp/?page=2`). So a page-flip silently drops `cache`, `run` and `profile`.

Why that is a wrong number rather than a wrong link: from this arm's own preset
(`/htmx/plp/?cache=cold`) a click on "2" lands on the **warm tier**, while the injected chrome
— rendered server-side against the original search and *outside* the swapped subtree — still
reads `cache: cold`. The address bar and the instrument disagree about one visit, in the
flattering direction. It also breaks ADR-0005 §3's planned `plp-paginate` entry before it is
written: the measured flip drops `run`, so it lands in a different KV namespace than its own
priming load.

Fix direction: `pageHref` should start from the request's own query and set `page`, which
means threading a `search` option from the caller (the master renders one fixed condition, so
the reference needs the option before any variant can use it). The same applies to the facet
hrefs (`href="?genre=Jazz"`), which are moot until the edge implements those params.

**I did not diverge in the variant**, for the reason (i) is not diverged from either: the
master emits these exact hrefs and the identity guard compares them at page 1, so a
variant-side fix would be a silent disagreement with the contract at the one condition
anything checks. I corrected **my** copy of the comment to state what the code does, and added
a leg pinning the current shape so the reference fix cannot land on one side only.
