Two things, read separately:

1. **The paint spike left run 0.** Run 0's with-chrome first paint is 744 ms, 40 ms over
   the median and the second-largest of seven, where the four artifacts before it put
   their largest sample there at 364, 96, 100 and 232 ms over their medians (`jq` over
   each: run 0 minus the stored with-chrome median, `770a6d8` first, `7c5be98` last;
   this artifact's run 0 is 40 over and its largest, run 4, is 212 over). The largest sample this time is run 4 at 916 ms, a
   with-chrome visit in the middle of the probe with no long task beside it and the
   without-chrome visit of the same pair at 592 ms, the fastest of its seven: a plane or
   network excursion of the kind addendum F's order-of-magnitude scope exists for, not a
   first-visit shape. The without-chrome arm's largest sample is run 2 (644 ms), also
   not run 0. So the one-sided first-visit paint bias the 2026-11-01 unit named is not
   in this artifact, which is what the warm-up was for. One artifact is one artifact: with
   no bias at all the largest of seven lands off run 0 six times in seven, so a single
   non-run-0 maximum is weak on its own, and it is the four-for-four before it that gives
   this one its weight; the next mint is the second data point.
2. **The long task stayed at run 0.** 97 ms of long task on run 0's with-chrome visit,
   0 on every other visit in both conditions. That is the fourth deployed-plane artifact
   of five to carry a long-task sample at run 0 and only in the with-chrome condition
   (55, 57, 118, now 97 ms), and this time the browser process was warm when it ran.
   Run 0 is the modal position for that sample, not the only one: two of the four earlier
   artifacts carry a second with-chrome sample at run 5 (`7c5be98` 64 ms, `770a6d8` 51 ms,
   in the table above and in addendum L's 2026-11-01 note), so across the five
   deployed-plane artifacts there are six non-zero long-task samples, four at run 0 and
   two at run 5, none in the without-chrome condition. So the warm-up removed the paint
   spike and did not remove the run-0 long task, which says the two moved for different
   reasons: the paint spike went with the cold process, and whatever the long task is, it
   still lands on the first with-chrome visit of a warm process more often than anywhere
   else, with the paint of that visit otherwise ordinary. The 2026-11-01 record named the first place to
   look if run 0 still spiked: the chrome's three subresources (`/_pm/chrome.css`, the
   instrument mono, `/_pm/measure.js`) are stripped from the without-chrome document, so
   the warm-up never requests them and run 0's with-chrome visit is the probe's first
   request for each. Whether that path is edge-cached was unverified; it is now, below.
   What the 97 ms is spent on is not in the artifact (the observer records long-task
   duration, not attribution) and is not claimed here. A long task is main-thread time,
   so a slow fetch on its own cannot be it. The renderer-local firsts (a first parse of
   the stylesheet, a first decode of the variable font, a first compile of `measure.js`)
   are excluded by the probe's own design: every recorded visit opens a fresh context

   renderer process across contexts, so every with-chrome visit pays those three and six
   of seven report 0 ms; this record first named them as candidates and the verify-slice
   correctness lens struck them. What is left is state the browser shares across
   contexts (one network process, one GPU process: a first connection to the plane for
   those three paths, a first raster of the mono) or the plane's side (the edge's or the
   Worker's first serving of them). Candidates, not causes; the per-visit
   `cf-cache-status` the probe owes tests the plane-side one.
   The medians delta absorbs it as before (the published long-task constant is 0 ms, the
   band clause on the methodology page says "0–97 ms across the runs, every non-zero
