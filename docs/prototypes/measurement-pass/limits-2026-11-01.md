# The constant's two stated limits, closed (post-runbook unit 1, 2026-11-01)

PR-3 (2026-10-17) published the chrome constant measured on the deployed plane and
stated two limits its own verify-slice had named (`verify-slice-2026-10-17.md`, rows 9
and 10): no gate reconciled the published delta with the artifact's own runs, and the

## The gate

`admitChromeConstant` (`workers/front/lab/publish.mjs`) gains four refusal sites
between the finite-delta check and the provenance bar:

- `cc-runs-count`: each of `conditions.with.runs` and `conditions.without.runs` must
  be an array exactly `runsPerCondition` long. An absent `conditions` refuses here
  too ("holds no runs"), never admits on absence.
- `cc-usable-samples`: for each metric and condition, the number of runs carrying a
  finite value must equal `runsPerCondition`. The probe writes `null` for a paint it
  never observed, and a list of seven with one finite FCP would otherwise publish a
  one-sample median beside "7 runs per condition" (the verify-slice conformance lens
  proved it admitted; held the way the receipts gate holds `incomplete-run-set`).
- `cc-delta-mismatch`: for each of FCP, LCP, CLS, longTaskMs, the median of the
  with-chrome run values minus the median of the without-chrome run values must equal
  `deltaMedians[metric]` exactly.
- `cc-stored-median`: the runner writes each condition's `medians` beside its runs;
  for each metric, the stored with-chrome and without-chrome medians must equal the
  medians recomputed from the runs; checked after the delta, so a run edit that breaks
  both is named by the published figure (the verify-slice correctness lens found the
  field unread, so a hand-edited stored median published in the raw artifact; now refused).

The median rule is the runner's own, copied rather than imported because the front
Worker's build does not depend on `@pm/bench-runner`: `tools/bench-runner/src/receipt.ts`
`median` (the non-null values sorted ascending; the middle one when the count is odd,
the mean of the middle two when even), applied per metric by
`tools/bench-runner/src/chrome-constant.ts` `medians`, whose result the runner
subtracts to write `deltaMedians`. The gate counts a run value when it is a finite
number; the runner writes `number | null` and JSON carries nothing else, so "finite
number" and "non-null" admit the same values. Because the gate performs the same
subtraction on the same doubles, the comparison is `!==`, with no tolerance.

## The probe

`tools/bench-runner/src/chrome-constant.ts`: before `for (let run = 0; …)` the probe
now makes one visit through `probeVisit(browser, profile, url, "without")` whose
metrics are dropped on the floor. It is judged for the fragment sha like every recorded
visit (a chrome change before run 0 refuses with its own message), and it is the
without-chrome condition, so the condition the spike favoured is not the one that gets
warmed. The artifact's `method` array gains one sentence saying so, as its seventh entry, before
the scope sentence, which stays last.
The probe also refuses at mint what the gate would refuse at build: after the loop,
any run whose FCP or LCP is `null` (a paint the observer never saw) ends the probe
with a non-zero exit and no artifact, naming the run and condition, because the mint
is the costly step (a quiet window on the attested plane, about an hour) and a tool
that exits 0 for a measurement the gate will not publish lies at the point of use, the
rule the probe's own `--runs` check already states (the verify-slice seams lens named
the asymmetry). `pnpm --filter @pm/bench-runner build` wrote `dist/chrome-constant.mjs`;
`tsc --noEmit` exit 0.

What a warm-up can and cannot touch, stated: `probeVisit` opens a fresh context per
visit (`browser.newContext(profileContextOptions(profile))`, ADR-0001 section 4), and
the probe is addendum S's stated exception, routing in both arms (`page.route` on the
document and the beacon), which turns the HTTP cache off within every visit; so no
cache rides from the warm-up into run 0 either way. What was cold was the browser
process (one `chromium.launch()` per probe), and that is what the warm-up heats. The
chrome's own subresources (`/_pm/chrome.css`, the mono, `measure.js`) are stripped from
the without-chrome document, so the warm-up never requests them; whatever is cold on the
plane's side for those three paths is still first hit at run 0's with-chrome visit, and
if the re-probe still spikes there, that is the first place to look.

## What this unit does not do

- It does not re-mint. The published constant stays `770a6d8`'s +72 ms; the probe
  change only takes effect at the next mint, which must wait for this unit's merge, the
  plane attesting its SHA, and a quiet deploy window (`constant-2026-10-17.md` has every
  command; about an hour including the identity gate). That re-probe is a follow-up PR.
- It does not hold every run. A run edited so that both medians stand is invisible to
  the gate, as it is to any reader of the delta; sabotage row P6 states it before it
  runs, and `pnpm bench reproduce` plus review are what hold it.
- It does not test the warm-up visit. No test drives the probe's visit sequence (a
  browser against an attested plane); sabotage row W1 states it. The re-probe is the
  proof.
