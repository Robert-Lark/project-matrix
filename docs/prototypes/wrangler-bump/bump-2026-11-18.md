# The wrangler bump, 4.110.0 to 4.164.0 (post-runbook unit 2, 2026-11-18)

One lockfile change, made in the worktree `.claude/worktrees/wrangler-bump` off
`origin/main` = `76b4678` (PR #95, the re-probe), and the verification that IS the
unit: `pnpm run check`, then the origin suite alone in both modes, every run recorded in
`suite-runs-2026-11-18.md` with its front-log tail, and the two runs that hung dissected in
`hang-2026-11-18.md`. Every figure below is from the command beside it, run on
2026-11-18 unless dated otherwise.

## The tree before anything

Porcelain 0 after the crate-image symlink (gitignored). `pnpm install --offline` 8.6 s,
`pnpm run check` 40 of 40 (31 cached, 13.45 s), no `[WARN]` line in either. The main
checkout sits on another session's `strip-em-dashes`; nothing there was touched.

## The release, and the gate it had to pass

`npm view wrangler version` printed `4.164.0`, the version wrangler 4.110's own crash
banner named on 2026-11-17; `npm view wrangler dist-tags` has `latest: 4.164.0`.
`npm view wrangler time` gives the publish times:

| version | published (UTC) |
|---|---|
| 4.110.0 | 2026-07-09T18:25:09Z |
| 4.159.0 (the 2026-11-09 brief's "current") | 2026-11-09T15:01:40Z |
| 4.164.0 | 2026-11-17T11:15:02Z |

The resolution ran at 2026-11-18T16:08Z, about 29 hours after the publish. That matters
because of a gate the brief did not name: `pnpm-workspace.yaml` carries a
`minimumReleaseAgeExclude` list naming `wrangler@4.110.0` and `miniflare@4.20260708.1`,
which only makes sense if a minimum release age applies. `pnpm config get
minimumReleaseAge` prints `undefined` (pnpm 11.10.0), and pnpm's settings reference
(`https://pnpm.io/settings/dependency-resolution`, fetched 2026-11-18) says of
`minimumReleaseAge`: "Default: 1440", "Type: number (minutes)", "To reduce the risk of
installing compromised or defective packages, you can delay the installation of newly
published versions"; and of `minimumReleaseAgeExclude`: "If you set `minimumReleaseAge`
but need certain dependencies to always install the newest version immediately, you can
list them under `minimumReleaseAgeExclude`". So the default gate is a day, 4.164.0 was
five hours past it, and no exclude entry was needed. Had the unit run on 2026-11-17 the
install would have resolved 4.163.0 (published 2026-11-16T12:03Z) or needed an exclude
line. The two existing exclude entries now name versions nothing resolves; left in
place, a one-line follow-up, not this unit's change.

## How the bump was made, and the two things pnpm did that were not asked for

`pnpm --recursive update wrangler` (online, the root `.npmrc` pinning
`registry=https://registry.npmjs.org/`, CodeArtifact not involved) resolved 4.164.0 in
14.6 s, and left porcelain at 12 files: `pnpm-lock.yaml` plus the eleven workspace
`package.json` files, whose specifier it had rewritten from `^4.110.0` to `^4.164.0`. In
`variants/qwik/package.json` it also re-serialised the file, turning the `description`
field's JSON escape for U+2014 into the glyph itself (`git diff` showed the escape on the
minus line and the glyph on the plus line), which `tools/repo-checks/test/no-em-dashes.test.ts`
would have refused. The eleven files were restored with `git checkout --`, then `pnpm
install` re-synced the lockfile's importer specifiers to `^4.110.0` while keeping the
resolution at 4.164.0, and `pnpm install --frozen-lockfile --offline` exited 0 on the
result. Porcelain after: ` M pnpm-lock.yaml`, one file, and the same after `pnpm run
check` (40 of 40, 4 cached, 15.5 s). `variants/react-next/cloudflare-env.d.ts`, the one tracked
generated types file, is unchanged because nothing in the check regenerates it
(react-next's `typecheck` is `tsc --noEmit`; `cf-typegen` is a separate script), and it is
now stale by its own header, `Runtime types generated with workerd@1.20260708.1`, on a
tree that resolves 1.20261117.1: the drift ADR-0004 names for that precedent.
Regenerating it is a second file change, deferred to the workers-types follow-up.

The alternative, keeping the eleven floor bumps to `^4.164.0`, was rejected: the brief
asks for one lockfile change, the floors carry no guard (the lockfile is the pin, as it
was), and a floor that moves on every bump is review churn. What is given up: a reader of
`package.json` alone still sees `^4.110.0` and learns the version from the lockfile.

The lockfile after:

```
wrangler@4.164.0          (three resolutions, by @types/node and workers-types peers)
workerd@1.20261117.1
miniflare@5.20261117.0-beta
esbuild@0.28.2            (wrangler's, and vite's optional peer under vitest in ten importers; see below)
```

`grep -c 'wrangler@4.110.0' pnpm-lock.yaml` is 0. `git diff --cached --stat` on the staged tree:
1 file changed, 872 insertions, 93 deletions (the first update's stat, `pnpm-lock.yaml | 987 +++++++++++++++++++++++++++----`, was
before the eleven specifiers were re-synced). `node_modules/.pnpm` still holds the 4.110.0 tree beside the new one (pnpm does
not prune the virtual store on update); the lockfile, not the store, is what the tree
resolves.

## What came with it

The `wrangler@4.164.0` block in the lockfile (`dependencies:`): `workerd 1.20261117.1`,
`miniflare 5.20261117.0-beta`, `esbuild 0.28.2`, `unenv 2.0.0-rc.24`,
`@cloudflare/unenv-preset 2.16.2`, `@cloudflare/kv-asset-handler 0.5.0`,
`blake3-wasm 2.1.5`, `path-to-regexp 6.3.0`, `@cspotcode/source-map-support 0.8.1`.
The bump also re-resolved packages outside wrangler's own tree. `esbuild@0.28.2`
appears 24 times in the staged lockfile and 0 times in HEAD's; `esbuild@0.28.1` 18 times
against 34 (`grep -c`): vitest's vite now resolves its esbuild peer to 0.28.2 in ten of
the importers (`tools/origin-suite` and `tools/repo-checks` among them) and keeps 0.28.1
in six, so the test runner's toolchain moved with this change too, and is split by
importer. `sharp` gains 0.35.5 beside 0.34.5 and `undici` 7.30.1 beside 7.28.0 (the
Miniflare 5 tree's). Whether `pnpm dedupe` would collapse the esbuild split was not
checked. Three things worth a sentence each:

- **The stable wrangler ships a beta Miniflare.** `npm view miniflare dist-tags`:
  `latest: 4.20260730.0`, `beta: 5.20261117.0-beta`. In wrangler's changelog the
  "Updated dependencies" lines carry Miniflare 5 from 4.117.0 on, `-alpha` through 4.149.0
  (38 lines) and `-beta` from 4.150.0 (21 lines), 59 in the range, so every wrangler release
  since 4.117.0 has run its local dev on a Miniflare 5 pre-release; 4.116.0 was the last wrangler on Miniflare 4 (`miniflare@4.20260730.0`, still Miniflare's
  `latest`; the first `miniflare@` line per version heading in the changelog cut). Pinning
  4.116.0 instead was the alternative, rejected: it keeps a stable Miniflare and 4.114.0's
  fix for the silent hang, and gives up 4.132.0's error surfacing (what made the hang
  legible here), 4.162.0's reload fix, and four months of the runtime CI deploys onto. `workerd` moves with it: 1.20260708.1 to 1.20261117.1.
- **One unmet optional peer, new.** `pnpm peers check` exits 1: wrangler 4.164.0 wants
  `@cloudflare/workers-types ^5.20261117.1` (`peerDependenciesMeta` marks it optional),
  the workspace has 5.20260718.1, declared by `variants/qwik` and `variants/react-next` at
  `^5.20260708.1`. The baseline install printed no `[WARN]`; the bumped one prints this
  and "2 deprecated subdependencies found: glob@9.3.5, node-domexception@1.0.0". The
  three Workers generate their runtime types from the installed wrangler
  (`wrangler types cloudflare-env.d.ts`, gitignored), so they do not use the peer;
  qwik and react-next type against the older package. A workers-types bump is a
  follow-up for those two variants (ADR-0004 rejects the package for the Workers), with
  its own typecheck, not this unit's one change.
- **The front Worker's local build attestation reads `dirty`** while the lockfile is
  modified (`front: stamped dist/_pm/build.json ... (76b4678, dirty)` in every local
  front log on the bumped lockfile; the run on the old lockfile, HEAD's bytes, stamped
  clean): expected, the stamp flips on any porcelain output, and nothing
  mints a receipt from a local plane.

## The entries that speak to the three plane classes, quoted

- 4.132.0, #14906: "Surface the original error message, name and stack when the dev
  server reports an internal error. Previously `wrangler dev` could exit with an empty
  `✘ [ERROR]` log that gave no indication of what went wrong (e.g. `Network connection
  lost.`, see #14641). These errors now include their original message, name and stack,
  so the failure is actually diagnosable." This is the empty banner of plane class (a),
  recorded in the 2026-10-17, 2026-11-01 and 2026-11-17 suite-runs files, four times in
  seventeen local runs (2 of 6, 1 of 6, 1 of 5).
- 4.114.0, #14593: "Fix dev proxy silently hanging or returning a misleading 503 on
  network errors for non-root-path requests. During `wrangler dev`, a transient network
  error on any request path other than `/` could be misclassified as the worker being
  reloaded, even when it wasn't: `GET`/`HEAD` requests would silently hang (with nothing
  logged) until the client timed out, and other methods would receive a misleading `Your
  worker restarted mid-request` 503. Such errors are now reported and surfaced
  immediately when the worker has not actually changed." The shape of plane class (c)
  as recorded (fetch legs at the 5 s wall, the front log silent, `POST /blog/admin/login
  503` as the last lines on 2026-11-01): the 503's body text was not recorded then, so
  whether it was this message is not known.
- 4.162.0, #16862: "Fix requests hanging when a local Worker reload finishes before an
  inflight request fails. Wrangler now immediately processes retriable requests when the
  replacement Worker is already ready."
- 4.153.0, #16476: "Update Undici to 7.30.1 to prevent a malformed HTTP response from
  crashing development tools."
- 4.118.0, #14936: "Stop `wrangler dev` starting new work after you stop it or it
  reloads ... in some cases the process could stay alive instead of exiting."
- Issue #14641 (`gh api repos/cloudflare/workers-sdk/issues/14641`, opened 2026-07-10,
  still open on 2026-11-18): "`wrangler dev` intermittently fails POST requests with
  `503 "Your worker restarted mid-request"` even though the worker never restarts ... a
  client sending requests on a steady ~5.000s cadence phase-locks with KJ's two default
  5-second connection timeouts inside the local dev proxy chain ... It is related to but
  distinct from PR #14593, which fixes the error classification". The request-drop
  mechanism, by its reporter's account, is not fixed by any release in the range.

What these say together: 4.164.0 should make a class-(a) crash name its cause and a
class-(c) hang report its failed requests instead of swallowing them; neither entry
claims the underlying failure is gone, and #14641 says one of them is not. The suite runs
are what test that, and run 2 of this unit (`hang-2026-11-18.md`) is the answer: the
hang is still there, and it now says so.
