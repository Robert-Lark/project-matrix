# The hang on wrangler 4.164.0, dissected (post-runbook unit 2, 2026-11-18)

Two of the five origin-suite runs on the bumped tree hung the same way, and this time the
plane left enough behind to say where. Every figure is from the command beside it; the
two CPU samples are trimmed into this directory (`workerd-sample-run2-2026-11-18.txt`,
`workerd-sample-run3-2026-11-18.txt`, the main thread and the inspector thread of
each). The runs themselves are rows 2 and 3 of `suite-runs-2026-11-18.md`. The first draft
of this record named the client on the front's inspector port as wrangler's own CLI and
missed the second blocked thread; two verify-slice lenses found both, and this text is
the corrected one (`verify-slice-2026-11-18.md`, rows 23 to 28 and 30 to 38).

## What a hung run looks like from the suite

Run 2 (crate mode, started 16:13:53Z) was signalled at 16:27:28Z after fourteen minutes
with no summary: 183 legs red, 0 green, 137 of them at the fetch legs' 5 s wall
(`grep -c -E ' 500[0-9]ms'`), 41 at the browser legs' 30 s wall, five at slower timeouts
(7.8 s, 7.8 s, 15.9 s, 47.4 s, 71.0 s), and one red in 2 ms, the last leg reported before
the signal (`composed-origin.test.ts`, "an unexpected variant error returns a generic
message"), whose failure message was cut off with the run; zero refused
connections, `data-plane`, `plp` and `security-floor` at "(0 test)". Run 3 (fixture
mode, started 16:30:51Z) was signalled at 16:36:37Z: 110 red, 76 at 5 s, 33 at 30 s, zero
refused (109 of the 110 at the two walls, the 110th at 30.4 s). The vitest forks were idle while they waited (`ps`: 0.0% CPU on all four), and
one was still alive about ten seconds after run 2's teardown, which the next pre-flight
caught.

Both are the third plane class of the 2026-11-01 and 2026-11-17 records by their suite
shape (nearly every fetch leg at exactly 5 s, nearly every browser leg at 30 s, zero
refused, no crash banner). What is different is what the plane says about it, below.

## What the front Worker's log says now

In the 4.110 records the front log simply stopped. On 4.164.0 it stops serving and then
reports every failed request, with the message 4.132.0's changelog entry promised (#14906:
"these errors now include their original message"):

```
✘ [ERROR] Error inside ProxyWorker (the affected request failed; the dev server continues): PUT http://127.0.0.1:8787/blog/admin/api/posts/ (failed after 1 attempt): internal error; reference = 0hejh8gksq7pjgkioooudovk
```

Run 2's `front.log` (982 lines at teardown): 213 `200 OK` responses, the last at line
531, then from line 540 on 147 such errors and not one more `[wrangler:info]` line.
By method, with the attempt count wrangler's dev proxy reports (`grep 'Error inside
ProxyWorker' | grep -c ': GET '` and so on):

| method | errors | attempts |
|---|---|---|
| GET (every path family: `/assets`, `/placeholder-static`, `/_pm`, `/placeholder-ssr`, `/vanilla`, `/astro`, `/`, `/react-next`, `/qwik`, `/how-it-was-built`, ...) | 123 | "failed after 3 attempts" |
| POST `/blog/admin/login` and the blog admin API | 22 | "failed after 1 attempt" |
| PUT, DELETE (blog admin API) | 1 each | "failed after 1 attempt" |

Run 3's `front.log` (1,724 lines): 704 `200 OK`, the last at line 1596, then 42 errors of
the same shape (20 GET at three attempts; 21 POST and 1 DELETE at one), no
`[wrangler:info]` after. "internal error; reference = <id>" is the text workerd answers
with when it cannot run the request; the dev proxy retries idempotent methods twice and
gives up on the rest at once.

The other ten Workers were fine throughout. Probed directly on their own ports while run 2
hung (`curl -m 3`): the edge answered its `/` 404 in 2.5 ms, every variant and the blog
answered 200 in 6 to 26 ms, the front alone timed out (`000` at the cap). The blog
Worker's log has zero `login` lines: the POSTs the proxy reported never reached it.

## Where the front was stuck

Each `wrangler dev` runs two `workerd` processes: the dev proxy, holding the public port
and the inspector port, and the user Worker's runtime, on loopback ports wrangler chooses.
During run 2's hang (`ps -p 70018,70019 -o pcpu,cputime,pid`, five seconds apart):

| process | ports (`lsof`) | CPU time 16:26:30 | +5 s | load |
|---|---|---|---|---|
| 70018, the proxy | `:8787`, `:9230` | 0:01.28 | 0:01.28 | idle |
| 70019, the runtime | `:65103-65105`, `:65133` | 1:16.28 | 1:16.90 | 12 to 13%, steady |

The runtime held 105 established TCP connections (`lsof -nP -a -p 70019 -iTCP`). Port
65105 was probed directly too (`curl -m 5`, four paths, all `000`), but wrangler's debug
log names it as the runtime's INSPECTOR endpoint (`NEW RUNTIME WEBSOCKET
http://127.0.0.1:65105/core:user:pm-front`, its line 313), not the Worker's HTTP entry
(`userWorkerUrl` port 65103, not probed), so those timeouts say only that the inspector
side was deaf. What places the wedge in the runtime is the sample.

`sample 70019 3` (macOS) found 14 threads (`grep -c -E '^ +[0-9]+ Thread_'`): the main
thread, eleven V8 worker threads parked in `__psynch_cvwait`, the inspector thread
workerd starts for the isolate (`workerd::server::startInspector`), and a V8 profiler
thread (`v8:ProfEvntProc`). Two of them were blocked for every one of the 1,996 samples, each in `kj::_::Mutex::lock` waiting for a write lock (the same mutex is likely, not shown: `sample` prints frames, not arguments) (`__psynch_rw_wrlock`, 3,761 leaf
samples in the tally: 1,765 on the main thread, 1,996 on the inspector thread):

```
main thread (isolate lock held):
  workerd::IoContext::runImpl / runInContextScope
  workerd::jsg::Lock::runMicrotasks
  v8::internal::Builtin_ConsoleLog
  workerd::(anonymous namespace)::handleLog
  v8_inspector::V8Console::Log ... V8RuntimeAgentImpl::messageAdded ... Frontend::consoleAPICalled
  workerd::Worker::Isolate::InspectorChannelImpl::sendNotification
  workerd::Worker::Isolate::InspectorChannelImpl::WebSocketIoHandler::send
  kj::_::Mutex::lock / _pthread_rwlock_lock_wait / __psynch_rw_wrlock

inspector thread:
  workerd::server::startInspector ... 
  workerd::Worker::Isolate::InspectorChannelImpl::WebSocketIoHandler::transmitLoop
  kj::_::Mutex::lock / _pthread_rwlock_lock_wait
```

The Worker's code was in `console.log` (the front logs one JSON line per dispatch,
`workers/front/src/index.js:103-104`, `log("info", "dispatch", ...)` at line 144). V8
reports a console call to every attached inspector session; workerd forwards it as a
`Runtime.consoleAPICalled` notification over the inspector websocket, and the send takes
a kj mutex. The thread whose job is to transmit on that websocket was waiting on a mutex
too. With the main thread holding the isolate lock while it waits, nothing else on that
isolate runs, which is what "every request after it times out" means; with the transmit
thread waiting, nothing goes out on the inspector websocket, which is why the inspector
side went deaf (below). Who holds the lock, and whether the two threads wait on the same one, is not in the sample.

Run 3's sample (`sample 74698 2`, the front runtime of that plane, 14.9% CPU, 58
established connections) has the same shape: the main thread on the same 14 frames from
`Builtin_ConsoleLog` to `WebSocketIoHandler::send` (`md5` `67699099b62279c98a0c6344e57bd37b`
in both excerpts by `awk '/Builtin_ConsoleLog/{f=1} f; /WebSocketIoHandler::send/{exit}'
<file> | sed -E 's/^[0-9]+ +//' | md5`), plus one frame above its mutex,
`workerd::XThreadNotifier::notify() const`; and the inspector thread blocked in
`workerd::XThreadNotifier::awaitNotification()` on a kj mutex, 1,648 of 1,648 samples.

The runtime's CPU is not the stuck threads: the profiler thread spends its samples in
`pthread_kill` and the main thread receives them in `_sigtramp` (229 and 222 in run 2's
tally), the shape of V8's sampling profiler signalling the thread it profiles.

## Who was attached to the inspector: the suite's own CPU profiler

The client on the front's inspector port is not wrangler's CLI. In run 2's front debug
log (wrangler writes one per dev process under `~/Library/Preferences/.wrangler/logs/`)
its only commands are `Profiler.enable` (line 1440), `Profiler.setSamplingInterval
{"interval":100}` (line 1607), `Profiler.start` (line 1627, at 16:14:08.291Z) and
`Profiler.stop` (line 4860, never answered). That is the origin suite's bench leg: it
builds an `InspectorCpuSource` over the local plane's inspector ports
(`tools/origin-suite/suite/bench.browser.test.ts:100`, inside a `beforeAll` whose timeout
is `300_000` at line 102) which, for each visit, connects to the serving Workers' ports
and sends exactly those commands (`tools/bench-runner/src/cpu.ts:179-180` enable and a
100 microsecond sampling interval, `:188` start, `:197` stop; the port list at `:227-237`,
the blog deliberately absent at `:218`). wrangler's own CLI does hold a socket on the
inspector port, but a different one: its ProxyController channel, authenticated by a
secret and routed apart from DevTools (`InspectorProxyWorker.js:84-89` in the 4.164.0
dist); every Worker has that one, the blog included.

So the timeline in the two hung runs reads:

| run | profiler starts in the front log (`grep 'SEND TO RUNTIME' \| grep -c '"method":"Profiler.start"'`) | last `Profiler.start` sent to the runtime (`SEND TO RUNTIME`) | last console event the runtime sent (`SEND TO DEVTOOLS {"method":"Runtime.consoleAPICalled"`) | heartbeat replies after it (`SEND TO RUNTIME {"method":"Runtime.getIsolateId"`, 10 s apart) | profiler socket closed | first proxy error |
|---|---|---|---|---|---|---|
| 1, fixture, green | 40 (every one stopped) | 16:13:10.599Z | 7,082 events, to the end of the run | answered | twice, 1005, reconnected | none |
| 2, crate, hung | 1 | 16:14:08.291Z | 205 events, the last at 16:14:09.048Z, 0.76 s after the start | 80 sent, 0 answered | 16:19:08.340Z, 1006, 300.1 s after connecting: the bench `beforeAll` hook's 300 s timeout | 16:19:52.056Z |
| 3, fixture, hung | 2 | 16:31:03.348Z | 693 events, the last at 16:31:03.556Z, 0.21 s after the start | 33 sent, 0 answered | 16:31:33.441Z, 1005 | 16:35:46.394Z (debug-log line 15276) |

(A first draft counted every `consoleAPICalled` line, 14,164, 410 and 1,386; each event
appears twice in the debug log, incoming and sent, and the halves match the front logs'
JSON lines, 7,074, 203 and 692.) Every green front log of this unit shows the same 40
profiler starts, each stopped: runs 1, 4 and 5 on 4.164.0, run 6 on 4.110.0, and runs 7
to 9 with the front's logging silenced (`grep` on each front debug log).

The front logs a dispatch after the upstream answers and before it returns the response
(`workers/front/src/index.js:143-148`), so the last console event marks the last upstream
answer: in run 2 eight dispatches were logged after the last served `200 OK` (front.log
lines 532 to 539) and never returned, which is what a thread stopping inside a later
`console.log` predicts. The inspector side going quiet and the wedge coincide at the
logs' resolution (the `[wrangler:info]` lines carry no timestamp); the proxy's first
report came 5 min 43 s (run 2) and 4 min 43 s (run 3) later, the time its retries took
to give up, not serving time.

## What this is, and is not

- **It is the hang class, made legible.** Same suite shape as the third class on
  2026-11-01 (three of six runs at load 5.7) and 2026-11-17 (one of five at load 1.02,
  the front log "silent after twenty seconds"), now with the front's failures named by
  the proxy, the stuck process found and sampled twice. On 4.110 the proxy swallowed the
  failures (4.114.0's changelog entry describes exactly that: GETs "would silently hang
  (with nothing logged)"), which is why the earlier records could only say "silent".
- **The bump did not fix it.** Two hangs in five runs on 4.164.0, against one in five on
  4.110 on 2026-11-17 and three of six on 2026-11-01; counts this small do not show the
  rate moving either way. The crash class (the empty banner) did not appear in this unit's
  runs; absence in eight runs on 4.164.0 is not evidence it is gone (four in seventeen on 4.110).
- **The candidate, with its evidence.** With the suite's own V8 CPU profiler attached to
  the front's isolate (100 microsecond sampling), a `console.log` notification to that
  profiler's inspector session and the inspector's transmit thread each block on a kj
  mutex, and nothing releases it. The strong part is the two blocked threads, the same
  shape in both samples. The timing is weak on its own: in the four green runs with
  logging on, 74 to 79% of the runtime's console events were sent inside a profiler
  session and 34 to 36% within a second of a `Profiler.start` (an `awk` over each front
  debug log tracking `SEND TO RUNTIME` starts and stops and the `SEND TO DEVTOOLS`
  console events), so both hangs landing within a second of a start is about a
  one-in-eight coincidence. The sharper timing signal is which session: run 2 hung in
  its first profiler session and run 3 in its second, while each green run completed
  40; that points at state early in a session's life, and it is two data points. Against it, or at least against any one factor alone: the profiler
  started and stopped 40 times in each of seven green runs, logging on in four of them;  the blog logs per request and never wedged, but the bench never profiles the blog
  (`cpu.ts:218`), so it is a harness fence and not a control. Named as a candidate, not a
  cause.
- **What is not shown.** Who holds the lock. Whether the profiler, the console call, or
  both are needed: the three silenced runs (7 to 9, no hang) kept the profiler (40 starts
  each) and dropped only the logging, so they vary one of the two; the discriminating run
  is the other one, the profiler off (the bench's `cpuSource` undefined, as it is against
  the deployed plane) with logging on, and it has not been run. Whether CI's origin job,
  which runs the same suite against a local plane, ever hit it: not checked here. No
  workerd or workers-sdk issue found names this shape (searches on 2026-11-18:
  "inspector deadlock", "console.log hang inspector", "DEVTOOLS WEBSOCKET CLOSED 1006"
  and "wrangler dev stops responding console.log inspector", zero hits each;
  "InspectorChannelImpl" in workerd, two hits, #6544 on `wrangler check` profile timing
  and #2564, a 2024 segfault on inspector reconnect, closed, neither a blocked runtime;
  the `ProxyWorker` searches hit #16216, #15447, #15317, #15203, #15452, #14641, #16348,
  #16741, none a blocked runtime).
- **What a reader can do with it.** Reproduce: run the suite alone on this tree until a
  run passes its fifth minute with no summary; `pgrep -fl 'workerd serve'`, take the one
  burning CPU (the profiler's signals), `sample <pid> 3`, and look for
  `InspectorChannelImpl::WebSocketIoHandler::send` above `Mutex::lock` on the main thread
  and `transmitLoop` or `awaitNotification` above `Mutex::lock` on the inspector thread.
  Disprove: a hung run with no `Profiler.start` in the front's debug log, or a hung run
  whose sample shows a different stack.
